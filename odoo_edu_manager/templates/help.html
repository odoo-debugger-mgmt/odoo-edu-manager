Help

This app manages multiple isolated Odoo instances as Docker containers, each with its own port, database and addons. Everything below is what's currently implemented.

Instances dashboard

The home page lists every instance this app manages, with:

  • Name — the instance name you chose (also its default database name).
  • Version — the Odoo version it's running.
  • Extras — Enterprise if Odoo Enterprise addons are mounted in, a dash otherwise. Design themes and VS Code debugging aren't shown here any more since every instance gets both unconditionally — see below.
  • Port — a link opening the instance directly, on its own hostname (see Hostnames).
  • DB — the database it's pinned to.
  • Status — running or exited.
  • Restore — live progress of a backup restore, if one was requested.

Per-instance actions:

  • Start / Stop — without deleting anything. Starting also re-attaches the instance to the shared network if that was recreated while it was stopped.
  • Logs — live docker logs stream (below).
  • Shell — a real odoo shell -d <db> inside the container, in the browser. env is bound to that database, exactly as via docker exec.
  • Terminal — a plain bash session inside the container: files, processes, ad-hoc commands. Not the Python REPL; that's Shell.
  • Users — lists the instance's users with a Connect as button per user.
  • Connect as admin — opens the instance already logged in, no password. The app has direct access to the container and database, so it mints a valid session the same way Odoo does after a real login.
  • VS Code / code-server — open the instance's generated workspace in the desktop app or in the browser. See Editors.
  • Edit — change settings and recreate the container (below).
  • Remove — deletes the container, after confirming. Leave "also delete data" unchecked to keep the filestore volume (e.g. to recreate the instance later); tick it to delete the filestore too, which cannot be undone.
  • Retry restore — shown when a backup restore failed; runs it again.

Creating an instance

From + New instance you can configure:

Instance name

Used as the container name (odoo-inst-<name>) and, unless overridden, the database name.

Odoo version

Pick a version already pulled locally, or type any other tag (e.g. 17.0) — it's pulled automatically the first time it's used.

Addons folders

One or more absolute host paths to your own custom addon modules, one per line. Each is mounted separately (/mnt/extra-addons-0, /mnt/extra-addons-1, …) and added to the container's --addons-path.

Browse opens a folder picker. If the folder you pick is a git repository, you also choose a branch and how to use it: Copy clones the repo locally and checks that branch out into its own isolated copy under the data directory, and mounts the copy — your working tree is never touched, you can run one instance per branch of the same repo side by side, and the copy is cached per repo and branch, so picking the same branch again is instant, but it's a frozen snapshot: nothing commits or pushes from it, and nothing ever refreshes it.

Worktree is the other choice once you pick a branch: instead of copying the repo, it creates a real git worktree — its own independent checkout of that branch, sharing history with your working copy but editable and committable on its own. Point the instance at it, edit the files on disk as normal, and the running instance picks it up exactly like any other addons folder — then git commit/git push from the worktree directory itself, in a terminal, same as any other branch checkout. Git won't let the same branch be checked out in two places at once: if the branch you pick is already checked out in the repo you browsed to (or in another worktree of it — common, since a real checkout is often permanently parked on one branch), you'll get an error naming where, unless you also fill in the optional new branch field — that forks a brand-new branch off the one you picked instead of checking the picked one out directly, which always works, including off the repo's own current branch. Worktrees aren't cleaned up automatically: removing an instance leaves the worktree directory in place (so you never lose uncommitted work), and deleting it later needs git worktree remove run from the original repo, not just deleting the folder. If the original repo is later moved or deleted, every worktree made from it stops working.

Important: Odoo requires that a directory's immediate children be actual modules — each with an __init__.py and a manifest (__manifest__.py/__openerp__.py). If none of a folder's direct children qualify, Odoo refuses the whole path with the path '...' is not a valid addons directory. Point each line at the folder that directly contains your modules, not a parent grouping several projects.

Include Odoo Enterprise

Unticked by default, so a new instance is Community and needs no GitHub access. When ticked, Enterprise is mounted at /mnt/enterprise-addons and prepended to --addons-path. Where it comes from depends on the next field:

  • Enterprise folder left blank — the app clones odoo/enterprise over SSH on the branch matching the version, the first time that version is needed, and caches it (enterprise/<version>/ in the data directory) for later instances. Needs an SSH key on this machine with access to that private repo.
  • Enterprise folder set — a local Enterprise checkout is used instead, for when you don't have SSH access to the repo. It works like addons folders: if it's a git repo you pick a branch, and that branch is copied out and used, leaving your checkout untouched. Mounted read-only.

Either way you still activate your subscription code from Settings → Activate inside the instance.

Design themes (automatic)

Every instance also gets odoo/design-themes, cloned on the matching branch and cached per version (design-themes/<version>/) — no checkbox. It's a public repository, cloned over HTTPS, so unlike Enterprise it needs no GitHub account or SSH key. Mounted at /mnt/design-themes-addons. If the version has no matching branch, or the clone fails (no network), it's skipped with a warning and the instance is still created — check the instance's Logs → Activity log tab if you need to know whether it succeeded.

Repository revisions

Enterprise and design themes are git clones, cached per version and shared across every instance of that version — by default each just tracks its branch's tip as of whenever it was first cloned. Odoo's own core addons normally come from the odoo:<version> Docker image instead (see below), but on versions where the app can safely swap them, core is a third git-sourced repo working the same way. This field lets you control exactly what each one resolves to:

  • Left blank ("Latest") — tracks the branch normally. Docker Hub's official images are not rebuilt on every upstream commit, and a shared branch clone isn't either, once cached — so "Latest" means "whatever the tip was last time this was fetched," not "always current." The Edit page shows the exact commit each repo is on right now, with a Refresh button that re-fetches the branch's current tip on demand. Refreshing updates the shared cache for every instance of that version tracking Latest, not just the one you clicked Refresh on — and an already-running container won't pick up the change until it's stopped and started again (Edit's Save & recreate does this, or Stop then Start).
  • A commit sha — pins that repo to exactly that commit, cached separately from the shared "Latest" clone, so pinning one instance never moves what any other instance sees. A pinned repo has no Refresh button on the Edit page (there'd be nothing for it to do); clear the field back to blank and save to return it to tracking Latest.

Odoo core only appears as a git-sourced option on versions listed in the field's hint text ({{ core_revision_versions|join(', ') }} at the time of writing) — entered here it's ignored on every other version. This exists because of a real failure mode: a git branch can reference addons files (new modules, changed code) that simply aren't in the matching Docker image yet, since the image isn't rebuilt on every commit. Cloning core addons fresh and shadow-mounting them over the image's own copy fixes that, but it's delicate — Odoo's internal module layout has genuinely changed between major versions in ways that broke this on a second version tested, so it's deliberately limited to versions confirmed to work rather than turned on everywhere. The Docker image itself is still used as the Python runtime either way; only the addons source changes.

Database backup (.zip)

Optional. If provided, it's restored the way Odoo's own Database Manager does it internally, run directly rather than through an HTTP upload:

  • Extract the zip and read dump.sql plus any filestore/ it contains.
  • Create an empty database with the encoding/collation Odoo itself uses.
  • Load dump.sql via psql.
  • Copy the filestore (attachments, documents, images) into place if the zip had one — some backups are exported without.

This runs in the background; the Restore column shows each step: waiting → extracting backup → creating database → loading database dump → copying filestore (N files) → done/error. Going direct sidesteps a real problem with large backups through Odoo's dev server, which could drop the connection mid-upload or, with debug mode, deadlock. Progress is kept in memory only — it resets if the manager restarts (restored data is unaffected).

Database name

Optional override — defaults to the instance name, or to the original database's name if the backup is a standard Odoo export with a manifest.json.

Port

Auto-suggested as the next free port from 8069, checking other containers' bound ports (including stopped ones, whose bindings persist) and the OS. You can override it. If a start later fails because the port is taken, the error names which container holds it.

Extra CLI arguments

Extra flags passed straight to the odoo command inside the container, parsed as a shell would (quote values with spaces). For example:

-i pos_modifiers --limit-time-real 0 --limit-time-cpu 0 --max-cron-threads 0 --log-handler odoo.addons.base.models.ir_attachment:WARNING --with-demo --dev=all

Appended after the app's own --database and --addons-path, so they can override them.

VS Code debugging (automatic)

Every instance runs Odoo under debugpy on an extra host port (auto-suggested, mapped from the container's 5678) — no checkbox, same as design themes above:

  • debugpy is installed with pip3 install --user each time the container starts, into the persistent data volume, so it's usually already there on restarts. Adds a few seconds to startup.
  • The debugger listens without blocking: Odoo serves HTTP immediately, and attaching is optional and can happen any time.

Editors: VS Code and code-server

Both buttons open the same generated multi-root .code-workspace:

  • Folders: the core Odoo addons (copied out of the instance's own odoo:<version> image via a throwaway container — exact, and needs no network), Enterprise and design-themes if included, and every custom addons folder.
  • If debug is on, a ready-made "Attach" launch config (type debugpy) pointing at the debug port, with path mappings so breakpoints in any of those folders — core included — match the code actually running in the container.
  • The core extraction is cached per version, like Enterprise and themes.

VS Code opens it in the desktop app through the vscode://file/ URI handler (registered by default when VS Code is installed).

code-server opens it in the browser. By default this targets a code-server container the app manages itself, started from Settings:

  • It mounts the data directory at the same absolute path it has on the host, so the workspace's paths and path mappings resolve unchanged.
  • The Python and debugpy extensions are installed automatically when the container is created (from Open VSX). Without them the attach config fails with Configured debug type 'debugpy' is not supported; Settings has a reinstall button if they go missing.
  • A login password is generated and shown on Settings. On native Linux the container uses host networking, which exposes it on every interface, so the password is not optional.
  • On Docker Desktop (macOS, Windows) host networking doesn't reach your machine, so the app publishes a port instead and points the debugger at host.docker.internal rather than localhost. Detected automatically from the daemon.

Settings also lets you point the code-server button at a code-server running elsewhere (a template with {workspace} substituted). If you do, the notes on that page about matching paths and the debugger's localhost apply.

Editing an instance

Edit lets you change version, addons folders, Enterprise options, database name, port, extra arguments, debug and repository revisions.

  • Saving recreates the container (stop, remove, run again) — most of these can't change on a live container.
  • The database (in the shared Postgres) and the filestore (a named Docker volume at /var/lib/odoo) both survive.
  • Design themes are re-resolved for the new version automatically.
  • A Repository revisions card at the top shows exactly what commit this instance is running for each git-sourced repo, with a per-repo Refresh button — see Repository revisions above for what Latest vs. a pinned sha means.

Skipping the database selector

Every instance starts with Odoo's --database=<db>, so visiting it goes straight to /web/login instead of the multi-database selector — even before that database exists.

Live logs

Each instance's Logs page streams docker logs --follow over Server-Sent Events: recent history first, then new lines as they happen, with a connection indicator (reconnects on container restart) and an auto-scroll toggle.

Shared infrastructure

  • odoo-manager-db — one postgres:17 container for all instances, created on first use.
  • odoo-manager-net — a bridge network connecting every instance to it.
  • Each instance gets its own database inside that Postgres, so instances stay isolated even though the server is shared.

Databases page

The Databases page lists every database in the shared Postgres, including orphans — left behind by removing an instance without "also delete data", or by a failed restore. Delete drops one outright (terminating open connections first). Deleting a database an instance still points at breaks that instance until you restore into it or edit it to point elsewhere.

Data directory

Clones, addons copies, uploaded backups, generated workspaces, activity logs and settings.json live in one directory: ~/.local/share/odoo-edu-manager when installed as a package, or data/ inside a git checkout, or wherever ODOO_EDU_MANAGER_DATA points. Everything in it is a cache or regenerated on demand; it's safe to delete between runs. There is no database for the manager itself — each instance's configuration is stored as labels on its container.

Agent access (MCP)

The manager is also available to agents over MCP: odoo-edu-manager-mcp (installed) or python -m odoo_edu_manager.mcp_server (checkout). For now it exposes one tool, list_instances. Destructive operations (removing instances, dropping databases, restores) are deliberately not exposed.

Hostnames, and running on macOS or Windows

Instances are opened on their own hostname — <db>.localhost:<port>. That gives every instance a separate cookie jar (cookies ignore ports, so ports alone would not). Linux resolves any *.localhost name to loopback; macOS and Windows only resolve localhost itself, so there you start the app with a base domain whose wildcard does resolve:

ODOO_EDU_MANAGER_BASE_DOMAIN=lvh.me odoo-edu-manager

and the instance links (Open, Connect as) use <db>.lvh.me. The manager itself stays at localhost:5001. lvh.me is a public domain that resolves to 127.0.0.1 — convenient, but somebody else's DNS. Windows means WSL2; native Windows is not supported (the in-browser Shell and Terminal are built on POSIX ptys).

Known limitations

  • No authentication on this manager UI — anyone who can reach its port can create, stop or remove instances, drop databases and run code. It binds 127.0.0.1 for that reason; don't put it on 0.0.0.0 on a shared network.
  • Runs on Flask's development server — fine locally, not for exposing beyond this machine.
  • Restore progress and anything beyond Docker labels isn't persisted across a manager restart.
  • The app has been run on Linux and, via a container, on the Ubuntu userland WSL2 uses. The macOS-specific code paths are tested, but it has not been run on a Mac.
